## 1. P01 到底在解决什么

P01 不写业务功能，只做三件事，但每件都是后面 14 个阶段的地基：

| 要解决的问题           | 不做的后果                                     |
| ---------------- | ----------------------------------------- |
| **把 proto 契约钉死** | 4 个 RPC、事件类型、字段号一旦变更，两侧生成代码和 P02~P15 全部返工 |
| **让两侧代码生成都能跑通**  | 后面所有联调都建立在生成物之上，生成不通等于没开工                 |
| **让配置错误在启动时就炸**  | 缺 Secret 却带着空值跑起来，问题会推迟到线上才暴露（安全配置静默降级）   |

一句话：**P01 的产出不是"能用的功能"，而是"后面能安全开工的环境"**。

## 3. 实现思路：五个关键决策

### 3.1 proto 放仓库根，两端只引用不复制

```text
proto/rag_service.proto          ← 唯一来源
├── java-service/pom.xml          <protoSourceRoot>../proto</protoSourceRoot>
└── python-rag/Makefile           PROTO_DIR := ../proto
```

**为什么**：如果每个工程各放一份 proto，两边一旦不同步，就会出现"生成代码能编译、运行时字段对不上"的诡异问题。单向引用让"改契约"只有一个入口。

**代价**：Java 侧必须用 `protobuf-maven-plugin` 的 `protoSourceRoot` 指出去，不能用默认的 `src/main/proto`。已在 pom 注释里写明原因，避免后人"顺手挪回来"。

### 3.2 生成代码不入库

`.gitignore` 排除了 `target/`、`app/grpc_gen/*.py`，只保留 `.gitkeep` 占位。

**为什么**：生成物入库会诱发两个问题——① 有人直接改生成代码，下次生成被覆盖；② proto 改了但生成物没重新生成，代码看起来"没变"。让 `make proto` / `mvn generate-sources` 现场生成，任何"忘了重新生成"都会在编译期暴雷。

### 3.3 必填项一律写 `${VAR:}`，靠 `@NotBlank` 拦

这是 P01 最容易踩的坑，也是实现里唯一"反直觉"的地方。

```yaml
app:
  hmac:
    secret: ${HMAC_SECRET:}    # ✅ 缺省为空串，@NotBlank 拦得住
    # secret: ${HMAC_SECRET}   # ❌ 变量缺失时绑定成字面量 "${HMAC_SECRET}"
```

**为什么**：Spring Boot 在绑定 `@ConfigurationProperties` 时，对**无法解析的占位符**不报错，而是把 `${HMAC_SECRET}` 这个字符串原样当成值。它是非空串，`@NotBlank` 拦不住——服务会带着一个"看起来有值"的假 Secret 启动成功。

**代价**：每个必填项都要多写一个 `:`。这个约定写在 `application.yml` 头部注释和 `AppProperties` 类注释里，避免后人"简化"掉。

### 3.4 三层验证，而不是只有单测

| 层 | 手段                                  | 能证明什么                |
| - | ----------------------------------- | -------------------- |
| 1 | JUnit / pytest                      | 缺变量时**抛异常**          |
| 2 | 真实进程（`java -jar` / `python -m app`） | 进程**退出码非 0** 且日志含变量名 |
| 3 | `verify-p01.sh`                     | 上面两层 + 四项验收判据串起来     |

**为什么**：验收标准写的是"**启动失败**"，而不是"某个类抛异常"。只做单测证明不了进程级行为——比如异常被 `try/catch` 吞掉、或者 Spring 把失败降级成警告，单测仍然是绿的。

第 2 层还有个细节：用 `env -i` 清空环境再跑，避免开发机上恰好存在同名变量导致测试假绿。

### 3.5 安全开关用 `@AssertTrue`，而不是删掉字段

`RAG_TLS_ENABLED` 只允许为 `true`。做法是保留字段 + 加断言：

```java
@AssertTrue(message = "RAG_TLS_ENABLED 不得为 false：一期禁止明文 gRPC（NFR-03）")
public boolean isEnabledRequired() { return enabled; }
```

**为什么**：删掉字段确实没人能配错了，但配置了 `RAG_TLS_ENABLED=false` 的人会收到"未知配置项"这种看不懂的报错。保留字段 + 明确断言，报错直接指向变量名和原因。

同时补了一条**反向护栏用例**：确认"不传该变量"不会被误判成 false 而拒掉服务启动。

### 3.6 protoc 版本一致性：规则只实现一次

**`app`**`/proto_version.py` 是版本规范化规则的**唯一实现**，`make proto` 和 pytest 都调它。

**为什么**：Maven 里 `protoc` 的 artifact 版本和它 `--version` 打印的版本**不是同一个字符串**：

| artifact 版本 | `protoc --version` |
| ----------- | ------------------ |
| `3.25.1`    | `libprotoc 25.1`   |
| `4.28.2`    | `libprotoc 28.2`   |

如果 Makefile 和测试各写一份转换逻辑，迟早漂移成"构建通过但测试失败"或反之。

## 4. 踩到的三个坑（都已修）

### 4.1 `${VAR}` 无默认值绕过校验

如上 3.3。这个坑的隐蔽之处在于**它不会报错**，只会让服务带着假配置正常启动。现在由「空串参数化用例」+「完全不传参数化用例」两条一起守：前者测 `@NotBlank`，后者测占位符没被解析成字面量，两种失效机制不同，不能互相替代。

### 4.2 bash 把全角标点吃进变量名

`verify-p01.sh` 第 5/6 步曾报 `exit=1`，看起来像"缺 HMAC_SECRET 时启动成功"，实际是被测服务**正确失败**了，崩的是脚本自己：

```bash
ok "退出码=$java_code，日志包含 HMAC_SECRET"
#                ↑ 全角逗号
# bash 在 UTF-8 locale 下把它并入变量名 → set -u 报 unbound variable
```

**修法**：变量一律 `${var}`；断言抽成 `assert_missing_var_fails()`，失败时打印进程输出末尾 20 行；脚本顶部加静态自检，扫描自身禁止该写法。

**教训**：中文脚本里 `$var` 后接标点必须加花括号。这类 bug 只在打印成功消息时爆炸，极容易被误读成被测代码的问题。

### 4.3 `RAG_TLS_ENABLED=false` 起初没拦

文档写了"不允许"，但代码只是普通 `boolean`，实测能正常启动并打印 `tlsEnabled=false`。已按 3.5 补齐。

**教训**：**注释约束不住配置**。凡是"文档说必须/禁止"的开关，都要有一条能在启动时炸掉的断言。

## 6. 现在能做什么 / 不能做什么

**能**：

- 一条命令在两侧生成 gRPC 代码，且版本一致
- 配置写错（缺必填 / TLS 关闭）立刻启动失败，报出变量名
- 本地起 MySQL 与 Qdrant 的依赖容器

**不能**（都在后续阶段）：

- 两侧**真正通信**（Channel 建立、TLS 握手在 P02）
- 连数据库、连 Qdrant（P04/P05）
- 任何业务接口（P06 起）
