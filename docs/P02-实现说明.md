## 1. P02 解决什么问题

P01 只证明了「两侧能各自生成代码」，但两个进程**从没说过话**。P02 要打通第一条真实链路：

```
Java（Spring Boot）  ──TLS──►  Python（grpc.aio）
        │                          │
   ManagedChannel            安全端口 + 拦截器
        │                          │
   HealthCheck  ────────────►  返回服务自身状态
   Chat（流式） ────────────►  骨架帧（CONTENT ×2 + FINISHED）
```

三条验收判据：① Java 能连上并拿到 `healthy=true`；② Chat 收到 ≥2 个 CONTENT + 1 个 FINISHED；③ 停掉 Python 后 Java 得到 `UNAVAILABLE` 且映射为 3001。

**这一阶段最重要的不是"能跑"，而是"错的时候能说清楚错在哪"**——所以错误码映射、证书校验、启动即失败都是本文的重点。

## 3. 实现思路（七个关键判断）

### 3.1 TLS 的难点在 SAN，不在证书本身

第一反应是"生成个自签证书就行"，但实际会卡在主机名校验：

- 现代 TLS **不再用 CN 做主机名校验**，只认 SAN 扩展；
- Java 侧按**连接地址**校验，用 `127.0.0.1` 连就必须有 `IP:127.0.0.1`，只签 `DNS:localhost` 照样握手失败；
- 失败时的报错是 `SSLHandshakeException`，看起来像"网络不通"，极难定位。

|                                                                  |                                                            |
| ---------------------------------------------------------------- | ---------------------------------------------------------- |
| 所以 `gen-dev-certs.sh` 里签了双 SAN，并**在脚本末尾自检**：\`openssl x509 -text | grep IP Address:127.0.0.1\`，缺一个直接报错退出。证书生成期就把问题挡住，而不是留到联调。 |

> 若将来换成只签域名的正式证书，用 IP 连接时必须配 `RAG_TLS_OVERRIDE_AUTHORITY`——这个开关已在 `GrpcClientConfig` 里留好，不是临时改代码。

### 3.2 客户端：Channel 单例 + deadline 收在门面里

`GrpcClientConfig` 把 Channel 做成 Spring 单例（gRPC Channel 本身支持多路复用，不需要连接池）。三个硬约束写在类注释里：

1. 只走 TLS——`RAG_TLS_ENABLED=false` 在 P02 之前已被断言拦住，没有明文分支；
2. 禁止 `InsecureTrustManagerFactory`，否则 NFR-03 的验收直接不成立；
3. 主机名校验必须保留。

`RagServiceClient` 的存在理由是 **deadline**：gRPC 不设 deadline 时，对端卡死会让调用线程无限期挂住。P09 的 SSE 转发一旦挂住就是"永远 loading"。把 deadline 收在门面里，业务代码**不可能忘**。

### 3.3 错误码：3001 与 3004 必须分开

| gRPC 状态             | 业务码  | HTTP | 含义                   |
| ------------------- | ---- | ---- | -------------------- |
| `UNAVAILABLE`       | 3001 | 503  | 连不上 / Python 没起来     |
| `DEADLINE_EXCEEDED` | 3002 | 504  | 调用超时                 |
| `UNAUTHENTICATED`   | 3004 | 500  | **连上了但认证失败**（P13 启用） |
| 其他                  | 5001 | 500  | 兜底                   |

看起来只是查表，但这决定**用户看到什么提示、运维往哪个方向查**。把 3004 并进 3001，会让"密钥配错"被误判成"服务挂了"，排查方向直接跑偏。所以映射表单独成类并配了用例。

### 3.4 Chat 骨架：为什么必须有连续 seq 和 FINISHED

骨架返回两句固定文本，看似敷衍，但两个细节是刻意的：

- **`seq` 从 1 连续递增**：前端靠它做乱序容错与丢帧检测，Java 侧靠它判断有没有丢帧；
- **末帧同时设 `finished=true` 与 `event_type=FINISHED`**：Java 按 `event_type` 分发、按 `finished` 判断结束，只设一个就会出现"一边判断不到"。

现在把这两条固定下来，P06 换成真答案时，Java 侧的解析逻辑不用改。

### *3.5* trace_id 三级兜底

优先级：**请求显式带 > 拦截器从 metadata 取 > 服务端生成**。

最后一层不能省：全链路追踪要求 trace_id **永不为空**，否则日志里出现空 trace 时无法把一次调用串起来。这个兜底是写测试时才发现的——直接调用 servicer（不经拦截器）时 `trace_id` 为空，测试立刻暴露。

### 3.6 配置校验升级：路径非空 ≠ 文件可用

P01 只校验 `RAG_TLS_CA_PATH` 非空。P02 真要用它了，所以两侧都加严：

- Java：`@AssertTrue` 检查 `Files.isReadable(Path.of(caPath))`；
- Python：`model_validator` 检查证书与私钥 `is_file()` 且可读。

失败时都报**环境变量名**。这样"证书路径写错"在启动阶段就暴露，而不是等到第一次握手才炸出一个看不懂的 `SSLHandshakeException`。

### 3.7 集成测试用真实 TLS，不 mock

`RagServiceClientIT` / `RagServiceDownIT` 都真的连服务。理由：P02 的目标就是握手本身，mock 掉 Channel 后证书 SAN、HTTP/2 协商、TLS 版本这些真正会出问题的地方全被绕过，测了个寂寞。

两个 IT 用 `@EnabledIfSystemProperty` 控制：默认 `mvn test` 会**发现但跳过**（`Skipped: 3`），由 `verify-p02.sh` 拉起服务后传 `-Dp02.it=true` 才真正执行。

## 4. 踩到的三个坑

### 4.1 surefire 根本不跑 `*IT.java`（假绿）

第一次跑 `verify-p02.sh`，第 4 步打印"✅ Java 集成用例通过"，但我去翻 `target/surefire-reports/`，**根本没有 `RagServiceClientIT` 的报告**。

原因：surefire 默认只匹配 `*Test` / `Test*` / `*Tests` / `*TestCase`，`*IT` 一个都不跑。脚本看到 `mvn` 退出码 0 就宣布通过——典型的假绿。

**修法**：pom 里显式 `<includes>` 加 `**/*IT.java`；现在默认 `mvn test` 显示 `Skipped: 3`，看得见"有 3 个用例被跳过"，而不是"没有这个用例"。

### 4.2 我又踩了一次「全角标点吃变量名」

`verify-p02.sh` 里写了 `ok "已就绪（PID=$SERVER_PID）"`，变量名后紧跟全角右括号，bash 在 UTF-8 locale 下把括号首字节并进变量名，`set -u` 直接报 `unbound variable`。

上一轮刚给 `verify-p01.sh` 加过静态自检，**说明靠记没用**。这次把自检块复制进了新脚本，它在提交前就抓到了另一处 `$PY_RUN（`。

### 4.3 增量编译导致的"薛定谔的绿"

中间有一次 `mvn test` 出现 10 个失败 + `NoClassDefFoundError: AppProperties`，重跑立刻全绿。追查下来是增量编译在 `target/classes` 留下不完整状态（与 IM 里反复跑 verify + 手工 mvn 并存有关）。

**处理**：`verify-p02.sh` 的 Java 步骤改成 `mvn clean test`，并在注释里写明原因——比起每次省 8 秒编译时间，宁可要确定性。之前还有一个 `NoClassDefFoundError` 引发的"以为代码有 bug"的误判，代价远大于这几秒。

### 5.3 附加验证：明文 gRPC 必须被拒（NFR-03）

服务端只调了 `add_secure_port`，没有 `add_insecure_port`。可这样自证：

```bash
cd python-rag
.venv/bin/python - <<'PY'
import grpc
ch = grpc.insecure_channel("127.0.0.1:50551")     # 故意用明文
try:
    grpc.channel_ready_future(ch).result(timeout=3)
    print("❌ 明文竟然连上了")
except Exception as e:
    print("✅ 明文连接被拒：", type(e).__name__)
PY
```

### 5.4 常见失败对照

| 现象                                                          | 原因                 | 处理                                                        |
| ----------------------------------------------------------- | ------------------ | --------------------------------------------------------- |
| `SSLHandshakeException` / `certificate_verification_failed` | 证书 SAN 不含所连地址      | 确认用 `127.0.0.1` 连接且证书含 `IP:127.0.0.1`；或改用 `DNS:localhost` |
| 启动时报 `RAG_TLS_CA_PATH 指向的 CA 文件不存在`                         | 路径写错 / 证书没生成       | 先跑 `gen-dev-certs.sh`                                     |
| `UNAVAILABLE`（3001）                                         | Python 没起 / 端口不对   | 看 `python -m app` 是否在 `listening`                         |
| `Skipped: 3` 且没有集成用例                                        | 没传 `-Dp02.it=true` | 用 `verify-p02.sh`，或手工加该参数                                 |
| 端口 50551 被占用                                                | 上次的服务没退干净          | `lsof -i:50551` 后 kill                                    |
